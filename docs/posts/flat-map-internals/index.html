Introduction

We use hash-tables a lot in software programming and there has been a strong desire for a more space and run-time efficient representation of a map among C++ users. I recently watched Matt Kulukundis’ CppCon 2017 talk, Designing a fast, efficient, cache-friendly hash Table, step by step. In this blog-post, I would like to explore the implementation details of the abseil library’s flat_hash_map data-structure.

The standard library’s unordered_set

Our starting point is the standard library’s implementation of a hash-table called the unordered_set. Here, we have a table(array) S, of size \(2^n\). The array elements \(S[0],\ldots,S[2^n - 1]\) are called slots. A new element is inserted into the table by hashing it, to find the correct slot. The element is stored at hash(item) % capacity() index. Two elements with the same hash-code, would have to be stored at the same slot; so we need a way to resolve collisions. unordered_set uses chaining, so each slot S[i] is more like a bucket, it is a linked-list of all items that hash to the same hash-code.

The H in the diagram is the hash-code. It is 64-bits. V is the actual value - the thing that we want to store. Because, each item lives in a separate node, different from the primary data-structure - the bucket array S, we say it has pointer-stability. No matter, what happens to the internals of the hash-table, the value doesn’t move, it lives at the same memory address. This is a property guaranteed by the standard. \(\phi\) denotes nullptr; it is used to indicate the end of linked-lists. The green nodes are all in the same bucket chain.

Now, if we look more closely, we are storing both the hash-codes and pointers for each element. That’s an extra 16-bytes per entry. When we iterate across the unordered_set, we actually end up walking this linked-list. That takes \(O(\texttt{size})\) runtime. The iteration order of this container is reproducible, for a given insertion order.

What can we do about this? Another approach is to have a doubly linked-list. Then, we can insert a new element without requiring a dummy slot. But, that adds another 8-bytes to everything. Also, it flushes out the L1d cache; the whole thing sounds expensive. So, we drop this approach. We are back to square one. We go back to the drawing board with our simplified view of the unordered_set without the dummy node. What did we gain? Since, we decided to drop the dummy node, that one less indirection on find() and insert(). We do we stand to lose? Iteration now take \(O(\text{size} + \text{capacity})\).

So, what did we lose, when we did this. Now, when the table resizes, we need to recompute the hash, which is potentially expensive, because we have to call the hash function on every element in the table. Is that really expensive? It depends on the type T. If its an int or a double computing a hash function is practically free. If its a big complicated type, yes it would be expensive. Its a trade-off. Now, when we run find(), we might have to run operator==() more often. The question now is, is equality comparison expensive? It depends on the type. If you’re comparing strings, then it is expensive. But, if you are comparing ints or doubles, equality is cheap to compute. On the plus side, users can get this back - you can put in a type T that defines a hash(T) member-function and can hash its own value. So, we didn’t technically lose any power, we just lost some convenience. Again, we gained some bytes of memory.
